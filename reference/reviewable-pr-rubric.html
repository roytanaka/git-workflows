The Reviewable PR — S·S·S Rubric

What a PR must be before it's worth your review time, and how to triage one that isn't. From Lesson 3.

The review ceiling (why size rules)

200–400
max LOC reviewable in one sitting
60–90 min
before attention falls off
70–90%
defects caught at that size
>500/hr
detection collapses past this rate

S · S · S — the three properties

  • SmallA few hundred changed lines at most — inside the ceiling above. Small stays short-lived.
  • Single-purposeOne outcome. State the purpose in one sentence with no "and" — if you can't, it's several PRs.
  • Self-describingTitle + description say what changed, why, what to check on the preview, and what's out of scope.

Triage decision (the incoming queue)

If the PR is…CallWhat you do
Small, single-purpose, self-describingReview nowReview against its stated intent + preview. Merge.
Big, or doing several things ("and… and…")Split itSend back; tighten the next brief into one-outcome PRs. Land shared parts first.
You can't tell what it does or whySend backAsk for a real title, purpose, and preview check before reviewing the diff.

The fix lives in the brief, not the PR

You scope tasks, you don't shrink diffs. PR size is decided before the agent writes code. A good brief carries: one outcome · a file/area boundary · a feature flag for anything too big to ship whole.
BRIEF TEMPLATE (give this to the agent)
Outcome (one shippable behavior): __________
Touch only:    ·   Do NOT touch: __________
If it won't fit in one small PR → split, or hide behind flag: __________
PR description must state: what, why, what to check on preview, out-of-scope

Slicing across parallel agents

  • Partition by feature + filesAgent A → billing; Agent B → settings. Different files can't textually conflict.
  • Land shared foundations first, aloneA shared field/component is its own PR that merges first — then features branch off it. Prevents duplicate work and the logical conflict from Lesson 2.
