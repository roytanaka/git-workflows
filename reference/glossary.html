Trunk-Based Development — Glossary

The shared vocabulary for every lesson. When a term is used in a lesson, it means exactly what it means here.

Trunk core
The single, shared main branch that all work integrates into — usually called main. The metaphor is a tree: the trunk is the one fat, long, central line; branches are short shoots off it.
Canonical: trunkbaseddevelopment.com
Trunk-Based Development (TBD) core
A workflow where developers integrate small changes into the trunk frequently (at least daily), keeping the trunk always releasable. The opposite of long-lived feature branches that drift for weeks.
Short-lived feature branch core
A branch off the trunk that exists only long enough to build a small change, get it reviewed, and merge it back — typically hours, at most a day or two. It exists for code review and CI checks, then is deleted.
trunkbaseddevelopment.com/short-lived-feature-branches
Merge to trunk core
Integrating a feature branch's change back into main. In TBD this happens often and in small pieces — DORA's marker of high performers is merging to trunk at least once a day with ≤3 active branches at a time.
dora.dev — trunk-based development
Continuous Integration (CI) practice
The practice TBD operationalizes: everyone integrates to mainline at least daily, behind an automated, self-testing build that proves the trunk still works.
martinfowler.com — Continuous Integration
Pull request (PR) practice
A proposal to merge a branch into the trunk, paired with a diff for review and automated checks. In your setup, this is where an AI agent's work lands for you to review before it touches main.
Preview deployment practice
A live, throwaway deployment automatically built from a branch or PR, with its own URL — so you can see the change running before merging. Created on every non-production push or PR, isolated from production (own environment variables/data), and surfaced as a link on the PR. Your primary review surface.
Vercel — Environments · Netlify — Deploy Previews
The three review signals review
What you confirm before approving a PR: CI checks (it builds + tests pass — internal consistency), the diff (how it's built — the approach), and the preview deploy (the change actually behaves for a user). All three are independent; the preview is the one most often skipped and the only one that proves behavior.
Releasable / "green" trunk core
The state TBD protects: the trunk could be deployed to production at any moment without breaking. Nothing half-finished is ever visible on it.
Feature flag (feature toggle) practice
A runtime switch that hides incomplete or not-yet-launched work. It lets you merge unfinished features into the trunk (keeping branches short) without exposing them to users — the move you make instead of holding a long-lived branch open.
martinfowler.com — Feature Toggles
Toggle types flags
"Feature flag" is one word for four tools with different lifespans. Release toggle: hides in-progress work (short-lived; remove after launch). Experiment toggle: splits users to measure a variant (lives as long as the experiment). Ops toggle: a kill switch / circuit breaker to disable a feature fast in production (long-lived, sometimes permanent). Permissioning toggle: gates a feature by user/plan, e.g. "Pro only" (permanent — a product rule, not debt). The first two are temporary scaffolding; the last two are meant to stay.
martinfowler.com — Feature Toggles
FlagClient (the wrapper) flags
A thin, team-owned module that every flag check goes through, so the vendor's SDK is named in exactly one file. Left to themselves, AI agents scatter raw vendor calls (e.g. posthog.isFeatureEnabled(...)) across the codebase; insisting on the wrapper buys a swappable backend, one place to enforce "default off," and a testable off-state — for the cost of one line in the brief.
LeadWise — flags in AI-generated code
Flag debt flags
A temporary toggle (release or experiment) left in the code after its job is done. Each one is a live if that doubles a code path forever — two ways to run, one of them dead. The discipline: every temporary flag gets an owner and a removal date at creation, and the cleanup PR that deletes it is part of the feature's "done." Ops and permissioning toggles are exempt — they're meant to stay.
martinfowler.com — Feature Toggles (managing toggle debt)
Deploy vs. release release
Two separate events you control independently. Deploy: the code is built and running on production infrastructure — automatic on every merge to main in a CD setup. Release: a user can actually see/use the feature — a separate decision, usually a feature-flag flip. Decoupling them is what lets unfinished work deploy to production while staying hidden.
martinfowler.com — Feature Toggles
Release from trunk release
The release model where production is simply the latest trunk — no release branch is cut. Suits a very high release cadence; when something breaks you roll forward (fix on trunk and ship again) rather than patch a side branch. The default for a continuously-deployed SaaS with no user-installed versions.
trunkbaseddevelopment.com/release-from-trunk
Roll-forward release
The fix discipline that comes with releasing from trunk: when a bug reaches production, you fix it on trunk (like a fast little feature) and let the normal merge re-deploy — never patch production or a side branch directly. Fixes always flow trunk → production, so the next deploy can't undo them.
Release branch release
A branch cut from the trunk at release time, "hardened," and deleted after release. Used when you must support a shipped version. Many continuously-deployed web apps skip these and release straight from trunk instead.
trunkbaseddevelopment.com/branch-for-release
Fix-forward vs. cherry-pick release
Fix-forward: fix a bug on trunk and release again. Cherry-pick: commit the fix to trunk first, then copy that one commit onto a live release branch. Rule: fixes flow trunk → release branch, never the reverse.
Squash and merge release
A merge style that collapses all of a PR's work-in-progress commits into a single commit on main. GitHub defaults that commit's message to the PR title — so the PR title becomes your permanent trunk history. Keeps the trunk log clean and one-line-per-change.
GitHub — About pull request merges
Conventional Commits release
A lightweight convention for commit/PR-title format: <type>: <description>, where feat: is a new capability, fix: a bug fix, chore: plumbing (and ! marks a breaking change). With squash-merge it makes the trunk log skimmable and is a free on-ramp to auto-generated release notes — without committing to the version-bumping machinery. Cheap to adopt when an agent writes the commits: put it in the brief.
conventionalcommits.org
Scaled vs. small-team TBD core
Small team: commit straight to trunk. Scaled: every change goes through a short-lived branch + PR review before merging. With AI agents committing, you run the scaled form — review is the whole point.
Branch protection / ruleset setup
A one-time configuration that stops anyone pushing directly to main and forces every change through a reviewed, tested PR. "Rulesets" are GitHub's modern, layerable form of the older "branch protection rules."
GitHub — About rulesets
Required status check setup
An automated check (build, tests, lint) that must pass before a PR can merge. The rule that keeps a red branch out of the trunk others branch from.
Up to date before merging setup
A protection rule requiring a PR to include the latest main (and be re-tested against it) before it can merge — so it was validated against what it's actually merging into, not a stale snapshot.
Reviewable PR (S·S·S) review
A pull request worth a human's review time: Small (a few hundred changed lines at most), Single-purpose (one outcome, statable in a sentence with no "and"), and Self-describing (says what changed, why, what to check on the preview, and what's out of scope).
Review ceiling review
The empirical limit on how much code a human can review well: roughly 200–400 LOC in a 60–90 minute sitting, yielding 70–90% defect detection; past ~500 LOC/hr detection collapses. The reason PR size is the master variable for review quality.
SmartBear — Cisco code-review study
Scoping the task / the brief review
How a director produces small PRs: deciding the PR's size before the agent writes code, by giving it one outcome, a file/area boundary, and a feature flag for anything too big to ship whole. PR size is set in the brief, not fixed at review time.
Work slicing / partitioning concurrency
Splitting work across parallel agents so PRs stay small and don't collide: partition by feature and files (non-overlapping turf), and land shared foundations first as their own PR before features branch off them. Directly defuses the logical conflict.
Logical (semantic) conflict concurrency
When two PRs each pass CI in isolation but break main when combined — e.g. one renames a function, the other (branched from older trunk) calls the old name. Git shows no textual conflict; only running the combination reveals it.
Merge queue concurrency
A mechanism that serializes ready PRs, stacks them on the latest main, re-runs required checks on the combination, and merges only what passes together — catching logical conflicts before they reach the trunk. Turn on when many PRs merge per day.
GitHub — Managing a merge queue
