Lesson 5 · Trunk-Based Development

Shipping From the Trunk

By the end of this lesson you'll know what "a release" even means in a continuously-deployed app, why your setup ships straight from trunk instead of cutting release branches, and the one lightweight commit convention that makes your trunk history readable.

In Lessons 1–4 you got a PR onto a trunk you keep releasable. Now the question is the one your whole job title contains: as release manager, what do you actually do to ship it? The surprising answer for your stack is "almost nothing on purpose" — and understanding why is the lesson.

1Deploy is not release

The single idea that makes continuous deployment sane: deploying code and releasing a feature are two different events, and you control them separately.1

Deploy
Your code is built and running on production infrastructure. On a Vercel/Netlify stack this happens automatically the moment a PR merges to main — no button, no ceremony.
Release
A user can actually see and use the feature. This is a decision you make — often just flipping a feature flag on — and it can happen minutes or weeks after the deploy.

Because the two are decoupled, "incomplete" work is no longer a reason to hold a branch open. The code deploys to production the instant it merges; it simply stays dark behind a flag until you decide to release it.1 That's how a half-built feature rides safely on a trunk you keep releasable — the subject of Lesson 6.

2Two ways to cut a release — pick one

TBD gives you exactly two release models, and they're a genuine fork. You pick the one that matches whether you must support old versions.

Release from trunkyour default

Production is always whatever's on main right now. There's no release branch — a "release" is just the latest trunk going out. When something breaks, you roll forward: fix it on trunk and ship again.2

  • Fits a very high release cadence — many merges a day.2
  • Nothing to maintain, harden, or back-port.
  • Matches your stack: one always-live SaaS, no user-installed versions.
Branch for release

At release time you cut a release/x.y branch from a chosen trunk commit, harden it, and ship that. Trunk keeps moving; fixes are made on trunk and cherry-picked onto the release branch.3

  • For products with versions you must keep alive — a customer pinned to v2 while you ship v3.
  • "Branch only when necessary, late, and instead of a freeze."3
  • Real overhead: a branch to maintain and back-port to.
The trigger to switch — and it's the only one: cut a release branch when you owe a specific shipped version ongoing support that you can't just roll forward — e.g. an enterprise customer contractually pinned to v2.0 for six months while trunk races ahead to v3. Until that exists, a release branch is pure overhead. Note the high-frequency rule of thumb: even teams doing one release a day can still branch to cherry-pick fixes, but teams releasing faster than that "do not need (and cannot use) release branches at all."2 You're in the second camp.

3The roll-forward rule

Releasing from trunk comes with one discipline that feels strange at first: when a bug reaches production, you do not patch production directly or scramble on a side branch. You fix the bug on trunk — like a tiny feature, just fast — and let the normal merge re-deploy it.2 "No slow down around a release and bug fixes inline."2

The reason is a rule that holds in both models: fixes always flow trunk → production, never the reverse. If you patched production (or a release branch) and forgot to put the fix on trunk, the very next deploy would re-introduce the bug. So even when you do cut a release branch, you reproduce and fix on trunk first, then cherry-pick — never the other way around.3 (That's the hotfix question — Lesson 7.)

Your move as release manager: you don't "do a release." You keep the trunk releasable (Lessons 2–4), and shipping is the byproduct — a merge auto-deploys, a flag flip releases. Your active decisions shrink to two: is this trunk state one I'm happy to have live? and is now the moment to flip this feature on for users? Everything heavier than that — release branches, back-ports, version maintenance — you take on only when a version you must support forces your hand.

4Make the trunk history readable: one commit convention

You merge PRs with squash-and-merge: every branch's messy work-in-progress commits collapse into a single commit on main, and GitHub uses the PR title as that commit's message.4 So the PR title is your trunk history — the one line that lives forever. That makes it worth one cheap convention.

Adopt Conventional Commits, lightly: PR titles follow <type>: <description> in the imperative.5 You don't need every type — three carry almost all your traffic:

PrefixMeansExample PR title → trunk commit
feat:New user-facing capabilityfeat: add CSV export to the reports page
fix:A bug fixfix: stop dashboard crashing on empty data
chore:Plumbing — deps, config, tooling (no user impact)chore: upgrade test runner to v9

Other types exist (docs:, refactor:, perf:, test:) and a ! marks a breaking change5 — but start with the three above. Since your agents write the commits, this costs you nothing: put "title the PR as a Conventional Commit" in the brief, exactly like the no-Co-Authored-By rule. The payoff: a trunk log you can skim ("what shipped this week?" = read the feat: lines) and a free on-ramp to auto-generated release notes if you ever want them — without buying the version-bumping machinery now.

What you're not adopting: full semantic-release / auto-versioning tooling that computes version numbers and writes a CHANGELOG.md from commit history.5 That pays off for libraries and installed software with real version numbers — not a single always-live SaaS where "the version" is just "whatever's on trunk." Convention now; machinery only if a real need for a published changelog shows up.

5Practice A: tag the PR title

For each merged change, pick the Conventional Commit type its PR title should carry:

A new "Export to CSV" button on the reports page lets users download their data.
✅ feat: — a new user-facing capability. This is the line you'd skim later to answer "what shipped?"
The dashboard threw an error and showed a blank panel for brand-new accounts; now it shows the empty state.
✅ fix: — it repairs broken behavior. (Sound familiar? It's the bug the preview caught in Lesson 4.)
Bump the test runner from v8 to v9 and update the CI config. No change to what users see.
✅ chore: — plumbing with no user impact. Keeps the noise out of your "what shipped" view.

6Practice B: what's the release move?

You're the release manager. For each situation, pick what you actually do:

A PR is reviewed, CI green, preview looked right. You want it live.
What ships it?
✅ Just merge. Merging to main auto-deploys to production — there's no separate "release" step. (If the feature should stay dark, that's a flag, not a branch.)
A bug just reached production from the latest trunk deploy. Users are hitting it now.
How do you fix it?
✅ Roll forward. Fix it on trunk like a fast little feature and let the normal merge re-deploy. Fixes flow trunk → production, never patched in sideways.
An enterprise customer is contractually pinned to v2.0 for six months — no upgrades — while you keep shipping v2.x features on trunk for everyone else.
How do you support both?
✅ Cut a release branch. This is the one trigger: a version you must keep alive that you can't just roll forward. You harden release/2.0 and cherry-pick fixes onto it from trunk.

7Check yourself

1. In a continuously-deployed app, what's the difference between "deployed" and "released"?

Right. Decoupling the two is what lets unfinished code merge and deploy while staying dark behind a flag until you choose to release it.
Re-read §1. A merge auto-deploys the code to production infra; releasing it to users is a separate decision (usually flipping a flag). That gap is the thing you control.

2. For your setup — one always-live SaaS, no user-installed versions, many merges a day — which release model fits?

Yes. A very high release cadence with no versions to support is exactly the case that "does not need (and cannot use) release branches at all."
Re-read §2. Release branches earn their keep only when you must support a shipped version. With no installed versions and many deploys a day, they're pure overhead — you release straight from trunk.

3. A bug reaches production from trunk. What does the roll-forward rule tell you to do?

Exactly. Fixes flow trunk → production. Patching sideways risks the next deploy re-introducing the bug.
Re-read §3. You roll forward: reproduce and fix on trunk, then let the merge ship it. A fix that isn't on trunk gets undone by the next deploy.

4. You squash-merge PRs. Why bother titling each PR feat: / fix: / chore:?

Right. Squash makes the PR title your permanent trunk message; the convention makes that log readable. The auto-versioning machinery is the part you're deliberately not buying yet.
Re-read §4. Squash-merge collapses the branch into one commit titled by the PR; a Conventional title makes trunk skimmable. It does not auto-bump versions by itself (that's the extra tooling you're skipping), and it isn't required to squash.
