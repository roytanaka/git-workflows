Lesson 3 · Trunk-Based Development

The Reviewable Pull Request

By the end of this lesson you'll be able to look at any incoming PR and judge in seconds whether to review it, split it, or send it back — and you'll know the one move that produces small PRs every time: scoping the agent's task before it writes a line.

Lessons 1 and 2 made the trunk safe: every change arrives as a tested, reviewed PR, and concurrency can't break main. So your bottleneck is no longer "did an agent break the trunk?" — it's "how fast can I review?" This lesson is about making that fast and trustworthy. The lever is almost entirely PR size.

1Size is the master variable

The largest study of code review ever run — Cisco, ~2,500 reviews, analyzed by SmartBear — found a sharp ceiling on how much a human can actually review well:1

200–400
lines of code is the most a reviewer can examine effectively in one sitting
70–90%
of defects found at that size, over a 60–90 min review
500/hr
LOC inspection rate above which defect detection collapses

Past that ceiling you aren't really reviewing — you're skimming and clicking approve. A 1,200-line PR doesn't get reviewed four times as carefully as a 300-line one; it gets reviewed worse, because attention falls off a cliff after about 90 minutes.1 And the cost compounds: smaller PRs are also picked up faster, merge faster, and are far easier to revert if something slips.2

The trap with AI committers: an agent can produce 1,500 lines as easily as 150. There's no natural friction pushing the diff small the way there is for a human typing it. If you don't impose the size limit, nothing will — and "looks fine, approve" on a giant diff is how unreviewed code reaches a trunk you're personally signing off on.

2The three properties of a reviewable PR

Size is necessary but not sufficient. A PR you can review in a few minutes has three properties — remember them as S·S·S:

S
SmallA few hundred changed lines at most — inside the review ceiling above. Small naturally stays short-lived too, which is the whole TBD bargain from Lesson 1: tiny trips around the loop.3
S
Single-purposeIt does one thing. "Add password-reset endpoint" — not "add password reset, rename the user model, and bump three dependencies." If you can't state the PR's purpose in one sentence without "and," it's really several PRs.
S
Self-describingThe title and description tell you what changed and why, what to check on the preview, and what's intentionally out of scope — so you review against an intent, not by reverse-engineering the diff.

These reinforce each other: a single-purpose change is almost always small, and a small change is easy to describe honestly. When one breaks, usually all three do — that's your signal.

3You don't shrink PRs — you scope tasks

Here's the mindset shift for your role. You are not going to chop a 1,200-line diff into four after the fact — that's slow and wasteful. As the director, you produce small PRs the same way you'd produce good code from any contractor: by scoping the work before it starts. The size of the PR is decided by the brief you give the agent, not by anything you do at review time.

A good brief to an agent carries three things:

  • One outcome. A single shippable behavior — the "single-purpose" property, set at the source. "Build the password-reset email flow" is one outcome; "build account management" is twenty.
  • A boundary. Which files/areas it should touch, and what it must not wander into. This is also what keeps parallel agents off each other's turf (next section).
  • A flag for anything not yet shippable. If the outcome is too big to land safely in one small PR, the answer isn't a long-lived branch — it's to merge the pieces behind a feature flag so each piece is small, hidden, and on trunk. (That's Lesson 6; for now just know it's the escape hatch that lets "small" and "incomplete" coexist.)
Your steering lever: when a PR comes back too big or doing three things at once, the fix isn't in the PR — it's in the next brief. Send it back with "split this into the endpoint and the UI as two PRs," and tighten how you scope the following task. You're managing intent and boundaries, not diffs.

4Slicing work so PRs stay small and don't collide

You asked about several agents shipping several features in one day. Small + single-purpose is also what makes that safe, because it lets you hand each agent a non-overlapping slice. Two rules of thumb:

  • Partition by feature and by files. Agent A owns the billing page, Agent B owns the settings page. Different outcomes, different files → their PRs can't textually conflict, and they're each small enough to review on their own.
  • Land shared foundations first, alone. If three features all need a new User field or a shared component, that change is its own small PR that merges first. Then the three feature agents branch from a trunk that already has it — instead of three agents each inventing it and colliding.

Notice this directly defuses the logical conflict from Lesson 2: the rename-vs-old-name disaster happens when two agents touch the same surface from stale starting points. Non-overlapping slices + shared changes landed first means they rarely touch the same surface at all.

5Practice: triage the incoming queue

It's the start of your day and four PRs are waiting. For each, decide as the reviewer: Review now (it's reviewable), Split it (too big / doing several things), or Send back (you can't tell what it does). Click your call.

Add “forgot password” email endpoint
+118 −12 · 3 files · “Adds POST /auth/reset-request that emails a reset link. Preview: try it on /login → ‘Forgot password’. Out of scope: the reset form UI (separate PR).”
✅ Review now. Small (~130 lines), single-purpose (one endpoint), and self-describing (states what to check and what's out of scope). This is the S·S·S target — exactly what you want every PR to look like.
Account management
+1,460 −320 · 28 files · “Adds password reset, the settings page redesign, a new User.role field, and upgrades the auth library.”
✅ Split it. Four "and"s in the description and 1,460 lines — far past the ~400-line review ceiling. You can't review this honestly. Send the agent a tighter brief: the User.role field lands first as its own PR, then reset, settings, and the lib bump as separate small PRs.
Updates and fixes
+240 −90 · 9 files · “Various improvements.”
✅ Send back. It's near the size limit, but you have no idea what it does or why — it fails "self-describing." Reviewing it means reverse-engineering 9 files of intent. Ask for a real title, a purpose, and what to verify on the preview before you spend a minute on the diff.
Fix off-by-one in pagination total count
+9 −3 · 1 file · “Last page showed one extra empty slot; total count was inclusive. Preview: /users?page=last.”
✅ Review now. Tiny, single-purpose, self-describing, with a preview path to check. Small bug-fix PRs like this are the lifeblood of TBD — review and merge in minutes, keep them flowing.

6Check yourself

1. An agent hands you a 1,300-line PR that passed CI and looks plausible. Why is "looks fine, approve" the wrong move here specifically?

Right. The Cisco/SmartBear data puts the effective ceiling around 200–400 lines; a 1,300-line diff can't get a real human review, and you're the human gate of record.
Re-read §1. CI checks behavior, not intent — your review is the human judgment. And the research is clear that past ~400 lines defect detection falls off sharply, so a 1,300-line approval is effectively unreviewed code reaching your trunk.

2. A PR is 150 lines but its description is “Add password reset, rename the User model, and bump three deps.” It’s small. Is it reviewable?

Exactly. Small is necessary, not sufficient. The "and … and …" is the tell: this is three PRs wearing one coat. Send it back to be split.
Size isn't the whole story (that's why it's S·S·S, not just S). This PR does three unrelated things — it fails single-purpose, so a problem in one change muddies review of the others and you can't revert them independently.

3. A PR comes back doing far too much. As the director, where does the real fix live?

Yes. PR size is decided by the brief, not at review time. Your job is intent and boundaries; you send this one back and tighten the next task's scope.
Re-read §3. You're the director, not the committer — you don't hand-split diffs, and a blunt line-count rule blocks legitimate changes too. The lever is scoping the task (one outcome + a boundary) before the agent starts.

4. Three agents each need a new User.plan field for their feature today. What's the move that keeps PRs small and avoids them colliding?

Right. Shared foundation first, alone; then fan out across non-overlapping features. That keeps every PR small and stops three agents from inventing (and colliding over) the same change.
Re-read §4. Three agents each adding the same field is exactly the duplicate-work / logical-conflict trap — and a long-lived shared branch violates TBD outright. Land the shared change first as its own PR, then branch the features off it.
