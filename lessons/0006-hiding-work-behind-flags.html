Lesson 6 · Trunk-Based Development

Hiding Work Behind Flags

By the end of this lesson you'll know why a feature flag is the thing that lets unfinished work ride on trunk — the move you make instead of holding a branch open — the four kinds of toggle and how long each should live, the one piece of architecture you insist your agents use, and the discipline that stops flags from becoming permanent debt.

Lesson 5 ended on a promise: code merges, auto-deploys to production, and then sits dark until you decide to release it. This lesson is the mechanism that makes that possible. A feature flag is the small switch that lets a half-built feature live safely on a trunk you keep releasable — and it's what the whole short-lived-branch model quietly depends on.

1The flag is what you reach for instead of a long branch

Lessons 1–2 told you branches must stay short — hours, not weeks. But real features take longer than a few hours to build. So where does the "not finished yet" state live while the work is in progress? You have exactly two places to put it:

That's the whole trade. A long-lived branch and a feature flag solve the same problem — "this isn't ready to show anyone" — but the flag is the one that's compatible with everything in Lessons 1–5: small PRs, daily integration, a trunk that's always releasable, deploy decoupled from release.1 When you direct an agent to build something too big to finish in one reviewable PR, the instruction isn't "keep working on a branch." It's "land it in pieces behind a flag."

2Four kinds of toggle — and how long each should live

"Feature flag" is one phrase for four different tools, and the difference that matters to you is lifespan. Some are temporary scaffolding you must tear down; some are permanent parts of the product. Knowing which kind you just created is what tells you whether it's debt.1

Release toggle
Hides in-progress work so it can merge to trunk dark. The kind this whole lesson is about.
Lifespan: days–weeks · remove after launch
Experiment toggle
Splits users (A/B, % rollout) to measure which variant wins. Drives a decision, then you keep the winner.
Lifespan: the experiment · then remove
Ops toggle
A kill switch / circuit breaker — turn an expensive or risky feature off fast in production without a deploy.
Lifespan: long-lived, sometimes permanent
Permissioning toggle
Gates a feature by user or plan — "Pro accounts only." Really a product rule wearing a flag's clothes.
Lifespan: permanent · not debt

The two on the left are temporary by definition: a release or experiment toggle that's still in the code after its job is done is the flag debt you'll meet in §4. The two on the right are legitimately long-lived — an ops kill switch or a plan gate is doing ongoing work, not waiting to be deleted. Same mechanism; opposite expectations.

3The one rule of flag architecture: own the wrapper

Here's the failure mode that's specific to your setup, where agents write the code. Ask an agent to put something behind a flag and its default move is to reach straight for a vendor SDK and scatter calls like posthog.isFeatureEnabled('csv-export') across a dozen components.2 It works — and it quietly welds your codebase to that one vendor, with no single place to change a default, enforce a type, or test the off-state.

So you insist on one rule: every flag check goes through a thin wrapper your team owns — call it FlagClient — and the vendor's name appears in exactly one file behind it.2

// lib/flags.ts — the ONE file where a vendor name appears
import { posthog } from './posthog'

export const FlagClient = {
  isOn(key, fallback = false) {
    return posthog.isFeatureEnabled(key) ?? fallback   // default OFF
  },
}

// anywhere else in the app — no vendor in sight
if (FlagClient.isOn('csv-export')) renderExportButton()

Call sites never name the vendor. Swap PostHog for an env var — or for nothing — by editing one file.

The payoff is all leverage you care about as the director: you can swap the whole flag backend (even from a paid vendor to a free env var) without touching a single feature; you get one place to force "default off" so a missing flag can never accidentally expose unfinished work; and the off-state is trivially testable. None of this is extra work for you — it's a line in the brief, exactly like the Conventional-Commit title rule from Lesson 5:

The brief line that buys all of it: "Put the export button behind our FlagClient (key csv-export, default off). Don't call the flag vendor's SDK directly anywhere outside lib/flags.ts." This is the same skill as scoping a task in Lesson 3 — you're setting an architectural boundary in the instruction, before any code exists, so it never shows up as sprawl in the diff.

4Flag debt: every temporary flag gets an owner and a removal date

A release toggle is scaffolding. Once the feature is fully launched, the flag has done its job — and every release/experiment toggle you leave behind is a live if that doubles a code path forever: two ways the code can run, two things to test, one of them dead. Let enough of them pile up and your trunk is a maze of switches no one remembers the state of.1

The discipline is cheap and it's yours to enforce, because the agent won't volunteer it: at the moment a temporary flag is created, it gets an owner and a removal date. And "remove the flag" is not a someday-chore — the cleanup PR that deletes the flag and the dead branch of the if is part of the definition of done for the feature. In Lesson 5's vocabulary that's a small chore: or refactor: PR, reviewed like any other.

Watch for this on review: a PR that adds a flag but the feature it was hiding shipped weeks ago — or a flag with no stated owner or removal date. Both are debt being created in front of you. The fix is a sentence: "this is a release toggle; when does it come out, and who owns deleting it?" Permissioning and ops toggles are exempt — they're meant to stay.

5Do you even need a vendor? The decision ladder

Because agents reach for a vendor SDK reflexively, the most useful judgment you bring is knowing when not to. Most "hide this until it's done" needs are met by the cheapest rung. Climb only when a concrete capability forces you to — and since everything sits behind the FlagClient wrapper, the choice is reversible.

1
Env var / config togglestart here
A boolean in config, flipped by a deploy. Perfect when the flag only hides unfinished work and needs no runtime flip, no per-user targeting, no measurement. The "you don't need a vendor yet" baseline — and the rung agents skip straight past.2
2
A flag service — and PostHog is the pick
Climb here the moment you need any of: flip a flag without a deploy, roll out to a % of users, target by plan/user, a real kill switch, or run an experiment. For this greenfield SaaS, PostHog is the best single bet — flags + product analytics + session replay + experiments in one tool, ~1M flag requests/month free, with an open-source self-host escape hatch.3
Others, and when they'd win: Vercel Flags SDK — free "flags as code," Next.js-native, and can use PostHog as its backing provider, so it's not either/or.4 LaunchDarkly — enterprise governance/compliance; overkill for a solo greenfield. GrowthBook / Unleash — open-source, self-host, free but more ops to run. Statsig — unlimited free flags, but now OpenAI-owned (strategic uncertainty for a long-lived bet).5
Your move as director: default new "hide this" requests to rung 1 and let the agent prove it needs rung 2. The wrapper means picking PostHog today and replacing it with an env var (or vice-versa) tomorrow is a one-file change — so this is a low-stakes, reversible call, not a vendor marriage.

6Practice A: config toggle, or a flag service?

For each need, pick the lowest rung that actually does the job:

Hide a half-built Settings redesign so it can merge to trunk now. You'll switch it on in a deploy once it's finished. No targeting, no runtime flip.
✅ Config toggle. It only hides unfinished work and flips at deploy time — the rung-1 baseline. Reaching for a vendor here is the reflex to resist.
Show a new onboarding flow to 10% of new signups and compare activation against the old one for two weeks.
✅ Flag service. Percentage rollout plus measuring a result is an experiment toggle — exactly the capability you climb to rung 2 for.
A third-party billing widget gets flaky in production. You want to switch it off in seconds — without waiting for a deploy.
✅ Flag service. "Off in seconds, no deploy" is a runtime kill switch (an ops toggle). A config toggle can't flip without shipping, so it can't do this job.

7Practice B: name the toggle — and is it debt?

Pick the type, and notice which ones you'll have to schedule for removal:

Gate the in-progress CSV export so it merges to trunk but stays invisible until it's finished.
✅ Release toggle — temporary scaffolding. Give it an owner and a removal date now; the cleanup PR is part of "done."
Show pricing-page variant B to half of visitors and measure which converts better over two weeks.
✅ Experiment toggle — lives only as long as the test. Once a winner's picked, keep it and delete the flag. Also debt if it lingers.
A switch that instantly disables the recommendation engine if it starts overloading the database.
✅ Ops toggle — a kill switch. Legitimately long-lived; it's doing ongoing safety work, not waiting to be deleted. Not debt.
Only Pro-plan accounts can open the audit log.
✅ Permissioning toggle — a product rule, permanent by design. Don't schedule it for removal; it's not debt.
