Lesson 2 · Trunk-Based Development

Protecting the Trunk for Parallel Agents

By the end of this lesson you'll know the exact day-one settings that let several AI agents open several PRs in a single day without breaking main — and you'll understand the one subtle failure (the logical conflict) that a merge queue exists to stop.

In Lesson 1 you ran the loop once. Now run it three times at once. Three agents, three features, three short-lived branches, all aiming at the same main in the same day. TBD is built for this — but only if the trunk is protected. An unprotected trunk plus concurrency is exactly how "loose Git" produces a broken production.

1The scenario, and what goes wrong unprotected

Picture your greenfield repo with no rules on main:

  • Agent A pushes straight to main — no review, no preview, no CI gate. A half-finished change is now in your releasable trunk. Rule broken on day one.
  • Agent B's tests never had to pass before landing. main goes red; now Agent C branches off a broken trunk and inherits the breakage.
  • Two agents force-push and one silently overwrites the other's commits.

None of this is a Git flaw — it's the absence of a gate. The fix is a one-time configuration you do before any code exists: branch protection on main.1

2The gate: branch protection on main

Branch protection turns main from "anyone can push anything" into "the only way in is a reviewed, tested PR." On GitHub you set this with a ruleset (the modern form of branch protection rules2). Here's your day-one checklist — tick them off as you reason through each:

Day-one protection for main

Require a pull request before mergingNo direct pushes to main. Every change — including every agent's — must arrive as a PR. This alone restores the loop.
Require status checks to passCI (build + tests) must be green before merge. A red branch can't poison the trunk that others branch from.1
Require branches to be up to date before mergingA PR must include the latest main before it can merge — so it was tested against what it's actually merging into, not a stale snapshot.
Require 1 approving reviewThat approver is you. This is the human gate from Lesson 1, encoded as a rule the agents can't skip.
Require conversation resolutionIf you leave a review comment, it must be resolved before merge — your feedback can't be silently ignored.
Do not allow bypassing / no force-push / no deletionThe rules apply to everyone, including admins and bots. No agent can force-push over main or delete it.
Auto-delete head branches after merge(Repo setting.) Step ⑥ of the loop, automated — merged branches vanish so they can't drift or pile up.

That's the whole gate. Notice what it does to your concurrency problem: with this in place, it doesn't matter how many agents push at once — every change is funneled through the same reviewed, tested doorway, single-file.

3Parallel branches aren't a TBD violation — they are TBD

A natural worry: "Lesson 1 said keep active branches low — DORA's marker was ≤3. Doesn't running three agents break that?" No. That guideline is about branch lifetime, not a ban on concurrency.3 Three branches that each live two hours are completely healthy. Three branches that each live two weeks are the problem. TBD wants many short trips around the loop, and many can overlap.

The real lever for safe concurrency is small + short. If each agent's change is small and lands within hours:

  • The conflict surface shrinks. Two small PRs touching different files don't conflict. Most parallel work simply doesn't overlap.
  • The merge window is tiny. The shorter a branch lives, the less main moves underneath it, so "update before merge" is cheap.
Your steering lever: when you direct several agents at once, give them non-overlapping slices — different features, different files. You're not managing Git; you're partitioning the work so the loops rarely cross. That's the job.

4The subtle killer: the logical conflict

Here's the failure that surprises people, and the reason "CI passed" isn't quite enough when many PRs land the same day:

Two PRs can each be green, and still break main when both merge.
Agent A's PR renames a function. Agent B's PR — branched from the same older main — adds a new call to that function's old name. Each PR's CI passed, because each was tested against a main that didn't yet contain the other. Merge both, and the trunk is red. Git shows no textual conflict — the files don't even overlap. This is a logical (semantic) conflict.

"Require up to date before merging" (checkbox 3) catches the simple case — it forces B to pull A's change in and re-test before merging. But it does so by making the agents take turns updating and waiting, which gets slow when several PRs are stacked up. GitHub's purpose-built answer is the merge queue.4

You don't need a merge queue on a brand-new repo with low PR volume — checkbox 3 is enough at first. Reach for it the moment "several agents, several PRs per day" becomes routine and you notice PRs stepping on each other. It's a toggle in the same ruleset, so you can turn it on later without rework.

5What this buys you

You configure the gate once, on day one, before any code exists. After that, concurrency is safe by construction: agents can fan out across features, and the only thing that gets serialized is the part that must be — the merge into main. Your bottleneck stops being "did an agent break the trunk?" and becomes "how fast can I review?" — which is a much better problem, and the subject of Lesson 3.
